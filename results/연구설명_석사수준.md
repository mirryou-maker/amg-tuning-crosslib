# 대수적 멀티그리드(AMG) 파라미터 튜닝 연구 — 한 페이지 설명

> 대상 독자: 수치선형대수를 아는 석사생. 그림 `concept_diagram.png` 참고.

## 무엇을 물었나

대규모 희소 선형계 $Ax=b$의 사실상 표준 전처리자인 **대수적 멀티그리드(AMG)**는
coarsening 방식, smoother, strength-of-connection threshold 같은 **내부
파라미터**에 성능이 크게 좌우된다. 그런데 대부분의 사용자는 이들을 라이브러리
기본값으로 둔다. 우리는 두 가지를 **실증적으로** 물었다.

1. 이 **내부 손잡이**를 튜닝하지 않아서 잃는 속도는 얼마인가? (선행연구가 다룬
   "어느 솔버를 쓸까"보다 한 단계 안쪽 문제다.)
2. 좋은 설정을, 실제 풀이보다 **값싼 특징**만으로 예측할 수 있는가?

## 어떻게 했나 (방법 상세)

**① 행렬 집합.** SuiteSparse에서 $10^4\le n\le5\times10^5$, 행당 nnz $\ge3$인
실수·정방 행렬을 뽑되 **그룹당 여러 개**를 골랐다. 이는 뒤의 group-wise 평가에
"같은 문제군 내부 구조"를 남기기 위함이다. AMG가 통하지 않는 순수 그래프
컬렉션(DIMACS10, SNAP 등)은 제외. 처음 150개, 뒤에 300개(엄격한 상위집합).

**② 파라미터 격자.** AMGCL에서 coarsening 3종 × strength threshold 4값 ×
relaxation 8종 = **88개 설정/행렬**. SPD는 CG, 나머지는 BiCGStab. threshold
경로가 coarsening 계열마다 달라 계열별로 처리.

**③ 계측 규율(핵심).** 각 설정을 상대잔차 $10^{-8}$까지 setup+solve로 계측.
우변은 **램프** $x^\*_i=1+i/n$의 $b=Ax^\*$ — 전부-1 벡터는 행합 0 행렬에서
$b=0$이 되는 퇴화가 있어 폐기. 프로세스 내 반복 후 **최솟값**(노이즈는 시간을
늘리기만 함). **노드당 단일 스레드**로 돌려 메모리 대역폭 경합을 차단(4개 동시
실행 시 36 ms solve가 116 ms로 부풀어 확인). 30초 벽시계 상한, 실패는 유형별
기록(diverged/maxiter/timeout/error). 계산은 DGIST iREMB 클러스터.

**④ oracle speedup.** 행렬마다 기본값과 최적설정이 모두 수렴한 경우에 한해
$T(\text{기본값})/T(\text{최적})$을 구한다(수렴한 설정만 대상).

**⑤ 특징(비용 등급).** Tier 0(구조: 크기·밀도·행nnz분포·밴드폭·패턴대칭·대각존재,
거의 공짜), Tier 1(값: 대각우세도·값비대칭 $\lVert A-A^\top\rVert_F/\lVert
A\rVert_F$·Gershgorin 반경·$|A|$에 대한 8스텝 거듭제곱 고유값 추정), Tier 2(대칭부
조건수 추정, 100–1000배 비쌈). 훈련셋 기준 스케일 정규화.

**⑥ 예측기.** 각 solve가 한 훈련 예제(행렬 특징 + 설정 원-핫). GBDT 2개(각
트리 120, 깊이 3): 성공 확률 분류기 $S$(전체 런), 로그 solve-time 회귀기
$R$(수렴 런만). 시험 행렬에서 전 설정을 채점해 $S>0.5$ 중 예측시간 최소를 선택
(없으면 $S$ 최대). **leave-one-group-out**으로 평가 — 같은 SuiteSparse group의
자매 행렬을 훈련·시험에 섞지 않아 성적 부풀림을 막는 정직한 분할이다.

**⑦ 교차검증·전이.** 같은 150행렬을 hypre BoomerAMG로 재실행(격자 36, 동일
규율). 라이브러리 간 설정 공간이 달라 config-수준 모델은 전이하지 않고, **행렬
수준 양**(풀리는가? / oracle 크기)만 라이브러리-독립 특징공간에서 전이한다.

## 핵심 결과

- **튜닝 이득이 크다**: oracle speedup 중앙값 **2.4배**, 상위사분위 6.4배, 최대
  **292배**. 최적 설정이 행렬마다 갈려(14가지) "기본값 하나 교체"로는 안 되고
  **행렬별 선택**이 필요하다. 게다가 31개 행렬은 기본값으로 아예 안 풀린다.
- **값싼 특징으로 예측 가능**: 예측기가 미지 행렬의 설정을 골라 **83% 성공**,
  oracle의 **43% 포착**(300행렬로 늘리면 89%/49%). 결정적으로 **Tier 0(거의
  공짜)만으로 충분**하고, 100–1000배 비싼 스펙트럼(조건수) 특징은 이득이 없다.

## 교차 라이브러리 검증 — 이 연구의 무게중심

- 튜닝 이득은 hypre에서도 나타나지만 **훨씬 작다**(중앙 1.6배). 왜? **AMGCL의
  거대한 oracle은 상당 부분 AMGCL 기본값이 약해서**다 — AMGCL oracle 상위 10개
  행렬은 전부 hypre 기본값이 이미 AMGCL 기본값을 이긴다.
- 따라서 **튜닝 이득의 크기는 라이브러리 간 전이되지 않는다**(oracle 순위상관
  0.24). 반면 **내재적 난이도(풀리는가)는 라이브러리 독립적**이다(어려운 행렬
  겹침 Jaccard 0.76). 예측기 전이 실험이 확증: "풀리는가" 분류기는 전이(+0.25–0.33),
  oracle 크기 회귀기는 전이 실패($\rho\approx0.2$).

**한 문장 결론**: 내부 AMG 파라미터 튜닝은 두 라이브러리 모두에서 실질 이득이
있으나, **그 크기는 라이브러리 기본값 품질에 반비례**하며 행렬 간 전이도 약하다.
난이도는 행렬의 성질, 튜닝성은 행렬–라이브러리 쌍의 성질이다.

## 장점 (기여)

1. **미개척 각도**: 선행연구가 "솔버 선택"에 머문 반면, AMG **내부 파라미터**
   공간을 체계적으로 튜닝하고 그 이득 분포를 정량화.
2. **정직한 방법론**: 특징 추출 비용을 이득에서 차감(대개 무시됨), group-wise
   분할로 성적 부풀림 방지(대개 무작위 CV).
3. **자기비판적 교차검증**: 두 라이브러리 비교로 "AMGCL의 292배" 같은 극적
   수치가 부분적으로 약한 기본값의 산물임을 스스로 규명 — 과대주장 교정.
4. **완전한 재현성**: 18,600 solve 데이터셋과 전 파이프라인 공개, `python
   reproduce.py` 한 줄로 모든 그림·수치 재현.

## 한계

1. **예측기가 oracle의 43%만 포착** — 특징이 일반 선형대수 성질만 담고 "AMG
   계층이 어떻게 만들어질지"를 못 담은 탓. AMG-인식 특징 도입이 다음 과제.
2. **CPU·두 라이브러리 한정** — GPU 백엔드(순차 smoother 불리, 최적 설정 이동)
   확장이 남음.
3. **150–300 행렬, 크기 대역 제한** — SuiteSparse 다양성 한계로 그룹 편중 없이
   그 이상은 어렵다.
4. **절대시간 교차비교의 한계** — 구현·CSR·Krylov 차이로 라이브러리 간 절대시간은
   경향으로만 해석하고, 상대량(speedup·상관·겹침)만 결론에 쓴다.
